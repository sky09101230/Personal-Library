## Context

见 `proposal.md`。当前 GitHub 来源扫描会克隆一个预配置仓库并发现其中所有 `SKILL.md`；候选校验、NAS 快照、摘要分类和人工发布已经存在。本变更只补充“发现一个结果并精确送入该流程”的入口。

## Goals / Non-Goals

**Goals:**

- 复用现有来源、后台任务和候选发布边界。
- 把 GitHub 请求、路径和许可证检查放在服务端信任边界内。
- 以少量请求满足人工搜索，不建立新的索引系统。

**Non-Goals:**

- 不做空关键词浏览、实时输入联想或批量导入。
- 不自动安装、执行或发布 GitHub 内容。
- 不保存搜索结果，不新增任务系统或 GitHub SDK。

## Decisions

### 使用 GitHub REST 代码搜索

服务端调用代码搜索并固定追加 `in:file filename:SKILL.md`，每页 20 条；相同关键词和页码使用 Django 缓存保留 3 分钟。相比仓库搜索后逐仓检查，这能直接证明结果对应 `SKILL.md`，也减少请求数。

请求使用 Python 标准库和服务器环境中的 `GITHUB_API_TOKEN`。上游错误单次返回给页面，不做自动重试；这比增加 SDK、队列或重试器更符合低频管理员操作。

### 导入时不信任浏览器中的仓库信息

浏览器只回传 `owner`、仓库名和文件路径。服务端重新校验字符和相对路径，再通过固定 GitHub API 地址确认公开仓库、默认分支最新提交、目标文件和可识别许可证，避免任意 URL 请求或路径穿越。

### 精确复用现有候选扫描

系统以仓库全名生成稳定且唯一的来源标识，并将目标目录和搜索时确认的提交传给现有扫描任务。扫描任务只归档该目录；如果默认分支已变化，则要求重新搜索，避免导入与管理员所见不同的内容。仓库许可证文件随候选快照保存。

### 保持人工发布为唯一正式入口

发现和导入只创建 `SkillCandidate`。正式 `SharedSkill` 和发布包仍只能由现有候选发布动作产生，因此网页正式检索与 MCP 无需增加新的可见性判断。

## Risks / Trade-offs

- [GitHub 代码索引不是全量且可能延迟] → 页面明确提示结果可能不完整，管理员仍可使用已有仓库来源扫描。
- [搜索接口限额较低] → 禁止空搜索、限制 20 条、缓存 3 分钟并不自动重试。
- [仓库在搜索与后台克隆之间变化] → 传递并核对提交；不一致时停止并要求重新搜索。
- [许可证检测不能代替法律判断] → 只把 GitHub 可识别许可证作为最低门槛，并保留来源、提交和许可证文件供审核。

## Migration Plan

新增服务器环境变量说明后部署代码；不需要数据库迁移。未配置 GitHub 令牌时只关闭新搜索能力，现有来源扫描和候选审核不受影响。回滚时移除入口和搜索服务即可，已创建的来源与候选仍按现有流程处理。
