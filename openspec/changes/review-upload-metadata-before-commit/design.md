## Context

当前网页上传在一个请求中完成 PDF 校验、DOI/BibTeX 预检、NAS 写入、正式文献建档和发布。文件可能达到 100 MB，确认页面不能要求浏览器再次上传；同时正式库、Library 和 MCP 都以 `CanonicalDocument` / `UploadedDocument` 为边界。

## Goals / Non-Goals

**Goals:**
- 文件只传输到 NAS 一次，确认后直接复用已存远端路径。
- 暂存批次严格归属上传者，正式表在确认前零写入。
- 保留现有 DOI 解析、去重、自动发布和最多四通道上传约束。

**Non-Goals:**
- 不改变 MCP、Zotero 或管理员 AI metadata 审核流程。
- 不增加后台队列、定时清理器或新的外部依赖。
- 不重新启用补充材料自动识别。

## Decisions

1. 新增最小的 `UploadReviewBatch` 与 `UploadReviewItem` 暂存模型。批次保存上传者和状态；文件项保存 NAS 路径、摘要及结构化 metadata。相比把 100 MB 文件留在进程缓存或签名 cookie，数据库暂存可跨请求、跨进程且能追踪待清理对象；它不属于正式文献表，也不被 Library/MCP 查询。
2. 浏览器先创建空批次，再由四个固定 worker 各自上传一个文件。每个文件请求独立返回解析结果和错误，避免单个大文件失败导致整个 HTTP 请求丢失其他结果。
3. 初始解析与 DOI 重解析复用现有 PDF evidence、DOI 选择、BibTeX 获取与解析函数。暂存阶段直接生成字段字典，不创建临时 `CanonicalDocument`；确认时把已核对字段复制到正式记录。
4. 缺标题是阻断错误；缺期刊是黄色警告且允许上传者明确确认。期刊字段对部分预印本、数据集或会议文献并不成立，强制要求会制造无法完成的批次；红/黄严重度也与此边界一致。
5. 确认操作在单个数据库事务内逐项执行既有 DOI/SHA 去重语义。新文件直接以暂存 NAS 路径创建正式上传记录，不再次 PUT；已有正文则删除多余暂存对象并关联上传者。数据库失败时不删除暂存对象，以便重试。
6. 取消操作逐项删除 NAS 对象，删除成功后才删除暂存记录。暂不增加自动过期任务；需要定时清理时再基于实际遗留量增加管理命令。
7. 四个通道和 metadata 表格使用紧凑的原生 CSS 布局，长文件名最多显示两行并保留悬停全文。全部上传 worker 完成后浏览器滚动到审核区；确认接口成功后直接进入 Library，不增加中间成功页或新的后端状态。

## Risks / Trade-offs

- [用户关闭页面会留下待确认批次] → 保留可追踪暂存行与取消接口；先观察遗留量，再决定是否需要自动清理。
- [确认重复文献时需要删除刚上传的冗余对象] → 删除失败则保留暂存项并中止确认，避免不可追踪孤儿文件。
- [外部 DOI 服务慢] → 每个文件独立请求且浏览器最多四并发，其他通道继续推进并显示服务端解析阶段。
- [工作树已有上传与补充材料修改] → 只修改网页主文献路径，并保持补充材料自动识别关闭。

## Migration Plan

1. 添加仅包含暂存批次与文件项的新迁移，不回填既有数据。
2. 部署模型、端点和页面后，新的网页上传进入确认流程；现有正式文献不变。
3. 回滚前先处理未确认批次；代码回滚后可删除新增暂存表，NAS 中已确认正式文件不受影响。
