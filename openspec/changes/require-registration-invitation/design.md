## Context

注册目前直接使用 Django `UserCreationForm` 创建并登录用户。项目已有 MCP 访问令牌的安全模式：随机生成明文、数据库只保存 SHA-256 摘要、后台页面仅展示一次明文，可直接复用这一做法。

## Goals / Non-Goals

**Goals:**

- 使用一个小型数据库记录支持生成、停用、过期和消费邀请码。
- 让账号创建与邀请码消费处于同一数据库事务中。
- 复用现有 Django 后台与令牌展示页面，不增加依赖或独立管理系统。

**Non-Goals:**

- 不处理已有账号，不增加邮箱验证、验证码或注册审批流。
- 不把有效期做成环境配置；本次固定为用户确认的 30 天。
- 不修改登录、找回密码或用户权限规则。

## Decisions

1. 邀请码使用 `secrets` 生成，数据库只保存 SHA-256 摘要。管理员创建后只看到一次明文；这与现有 MCP 令牌模式一致，也避免数据库泄露后直接获得可注册凭据。
2. 邀请记录保存创建人、备注、启用状态、失效时间、使用人和使用时间。后台负责生成和提前停用，不再增加新的工作人员页面。
3. 注册表单先给出友好的有效性提示；真正消费时使用带条件的数据库更新。账号创建和消费放在同一事务内，更新失败则回滚账号，从而保证同一码最多成功一次。
4. 新邀请码固定在创建时写入 `当前时间 + 30 天`。过期时间作为只读记录，避免后台误把默认期限改成长久在线凭据。

## Risks / Trade-offs

- [管理员离开生成结果页后无法找回明文] → 这是有意的安全边界；需要时重新生成一个邀请码。
- [邀请码转发给了非预期人员] → 管理员可立即停用；成功使用后自动失效。
- [部署代码但未执行迁移会导致注册报错] → 部署顺序先迁移，再重启应用；回滚代码前可保留新增表，不影响旧版本。

## Migration Plan

1. 创建邀请码表，不修改用户表和现有账号。
2. 执行迁移后重启 ASGI 服务。
3. 管理员生成邀请码并完成一次真实注册验收。
4. 如需回滚，先回滚应用代码；新增邀请码表可暂时保留，之后再按迁移流程处理。
