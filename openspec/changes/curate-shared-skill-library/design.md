## Context

现有 GitHub 同步在仓库内递归查找 `SKILL.md`，随后立即创建 `SharedSkill`、打 ZIP 并上传 NAS；独立 enrichment 流程已经能生成两句中文摘要、选择现有叶子分类并保护人工覆盖。正式库模型没有草稿状态，因此不能承担候选审核职责。参见 `proposal.md` 和 `specs/skill-library-curation/spec.md`。

## Goals / Non-Goals

**Goals:**

- 在正式 `SharedSkill` 之前增加一个来源无关的候选状态边界。
- 让 ZIP 投稿和 GitHub 扫描复用同一套安全检查、元数据解析、AI 分类和批准发布服务。
- 继续使用现有 NAS、DeepSeek、Git 和 Django 能力，不增加依赖。
- 让来源、快照、人工决定和发布结果可追溯。

**Non-Goals:**

- 不支持一个 ZIP 投稿多个 Skill、文件夹直传、私有 GitHub 凭据或 GitHub OAuth。
- 不让 AI 自动创建分类，也不在第一版引入自由标签、推荐分数、评论或版本协作。
- 不自动执行候选中的脚本，也不对 Skill 的科学正确性做自动保证。

## Decisions

### 1. 使用独立 `SkillCandidate`，不为 `SharedSkill` 增加草稿状态

候选记录包含来源类型、投稿者或 GitHub 来源、源路径与提交、内容指纹、私有快照路径、规范化元数据、AI 来源信息、分类人工锁定、校验消息、审核状态和正式 Skill 关联。正式列表和 MCP 继续只查询 `SharedSkill`，天然保证未发布隔离。

备选方案是在 `SharedSkill` 增加 `status` 并修改所有查询；这扩大了泄漏风险和回归面，因此不采用。

### 2. 所有候选保存不可变 ZIP 快照到独立 NAS 根目录

ZIP 投稿先在内存/临时文件中验证，GitHub 扫描则从每个 `SKILL.md` 所在目录生成 ZIP；通过后上传到 `NAS_WEBDAV_SKILL_CANDIDATES_ROOT`，默认与正式 `NAS_WEBDAV_SKILLS_ROOT` 分离。批准时从候选快照复制到正式根目录，成功创建发布记录后删除候选快照。

这比批准时重新克隆 GitHub 更可追溯，也避免上游变更造成“审核内容”和“发布内容”不同。代价是待审核候选占用存储；已发布和拒绝时清理快照降低长期占用。

### 3. 用标准库 `zipfile` 做严格边界校验

验证在任何解压或远端上传前完成：限制压缩文件 10 MiB、最多 200 个成员、总解压体积 50 MiB；拒绝绝对路径、驱动器路径、`..`、反斜杠、符号链接、加密成员，以及禁止的敏感/科研资产文件名与扩展名。只读取唯一 `SKILL.md` 文本用于元数据与 AI，不执行任何内容。

配置常量先固定在服务中；真实使用证明阈值不合适时再增加设置项。

### 4. 把现有元数据解析和 enrichment 提升为共享候选能力

增强现有 `_read_metadata`，在不引入 YAML 依赖的前提下支持引号值与 `|`/`>` 多行描述。候选先获得本地名称/描述，再调用现有 `generate_skill_enrichment`；调用失败只形成警告。管理员手工分类设置 `purpose_is_manual=True`，后续自动化只更新 AI 建议信息。

### 5. GitHub UI 从“同步发布”改为“扫描候选”

保留现有后台任务和进度模型，增加 scan operation 与管理命令。扫描按 `source + source_path` 更新候选：内容指纹未变化时保持状态；变化时保存新快照并回到待审核。原直接同步服务保留给兼容测试和维护命令，但不再由网页入口调用。

### 6. 批量批准仍逐条使用原子发布函数

每个候选独立发布：先把快照上传正式 NAS，再在事务中创建或更新 `SharedSkill`、`SharedSkillRelease` 和候选关联；数据库失败时删除刚上传的正式对象。批量操作逐条返回成功与失败数量，避免一个坏候选阻塞全部候选。

### 7. 用数据迁移建立有限的科研任务树

建立六个一级分类和有限的叶子分类；现有 `literature-search`、`literature-read` 原地挂到“文献与知识”下，主键和 Skill 外键不变。AI 仍只能从现有叶子分类选择，避免分类无控制增长。

## Risks / Trade-offs

- [ZIP 检测无法证明内容绝对安全] → 禁止高风险文件、从不执行候选内容、保持人工审核和正式发布隔离。
- [扫描大型仓库会产生较多候选快照和 AI 请求] → 内容指纹未变化时跳过上传与 enrichment；管理员按单个来源触发扫描。
- [AI 分类可能不准确] → 只允许选择预定义叶子分类，允许人工改正并锁定。
- [发布时 NAS 成功但数据库失败] → 捕获异常并删除新正式对象；候选快照保留以便重试。
- [拒绝后删除快照降低复核能力] → 保留候选元数据、指纹、校验和拒绝原因；用户修改后重新投稿。

## Migration Plan

1. 创建候选表并填充科研任务分类树；不迁移或重发任何现有正式 Skill。
2. 部署投稿、候选列表和扫描入口，现有正式下载保持可用。
3. 管理员按来源扫描现有外部仓库，先观察候选分布再选择发布。
4. 回滚应用代码时保留新增候选表不会影响正式库；回滚数据库迁移前必须确认没有待审核候选。
