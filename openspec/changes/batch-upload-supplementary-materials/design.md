## Context

当前网页上传以单个文件为单位：文件通过校验、写入对象存储、创建 `UploadedDocument` 后即发布其 `CanonicalDocument`。上传记录没有文件角色，且不能把同批次中的正文作为补充材料候选。详见 `proposal.md` 及本 change 的规格。

## Goals / Non-Goals

**Goals:**

- 在一次网页多文件上传中，按严格 DOI 证据将补充材料关联到已存或同批次正文。
- 仅将通过预检的补充材料写入对象存储和数据库，并给出逐文件结果。
- 维护正文默认下载和发布语义，避免补充材料成为独立文献。

**Non-Goals:**

- 不持久化未匹配补充材料，不提供待关联队列、后台重试或反向自动关联。
- 不使用 OCR、外部 API、大模型、模糊题名匹配或 ZIP 上传。
- 不改变 MCP 或 Zotero 的上传入口；它们继续按正文 PDF 处理。

## Decisions

### 以 `UploadedDocument` 文件角色表达从属关系

为 `UploadedDocument` 增加 `primary` 与 `supplementary` 角色，继续通过已有的必填 `canonical_document` 外键表示归属。这样不需要新增只有一个实现用途的 attachment 表，也不会允许未归属文件进入数据库。

备选方案是使外键可空并新增待关联状态。该方案需要额外处理发布、MCP 可见性、清理与权限，和“未匹配即不上传”的产品规则冲突，因此不采用。

### 以同批次预检建立临时正文候选集

在写对象存储前验证全部选中文件，提取其 DOI 和补充材料信号；候选集由库内已有正文和本批次识别出的正文组成。对每份补充材料只接受唯一的规范化 DOI 匹配。预检不创建数据库记录或远端对象。

同批次通过预检后，先依次保存正文，再保存其补充材料。单个文件的存储失败不会回滚无关文件；若正文失败，依赖该正文的补充材料标记为未上传。该策略在无对象存储跨文件事务的前提下避免孤立补充材料。

### 发布与读取只以正文为入口

正文成功写入才将文献发布。补充材料关联到既有文献但不改变其发布状态；默认预览与下载筛选正文角色。补充材料在文献详情中作为明确的从属文件展示。

## Risks / Trade-offs

- [补充材料没有可提取 DOI] → 拒绝上传并要求先获得可精确匹配的正文证据；第一版不以题名猜测归属。
- [PDF 文字提取增加请求时间] → 只提取必要页面和本地查询；不等待 OCR、外部服务或后台任务。
- [对象存储在后续文件失败] → 每个文件沿用现有失败清理；依赖失败的补充材料不开始写入。

## Migration Plan

1. 为上传记录增加带默认值的文件角色，历史记录全部迁移为正文。
2. 部署迁移和应用代码；现有文献的发布、下载与存储路径保持不变。
3. 若需回滚代码，保留新增列与其默认值，不删除已写入数据。
