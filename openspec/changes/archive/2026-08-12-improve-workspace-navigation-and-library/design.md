## Context

当前首页、文献库和“我的上传”都位于 `box_upload` 应用。文献库以 `CanonicalDocument` 为行并预取 `UploadedDocument`，而“我的上传”直接列出上传记录。对象存储删除已有统一入口，管理员删除流程已经采用“先删存储、再删数据库”的安全顺序。

## Goals / Non-Goals

**Goals:**

- 复用现有文献库查询、模板和对象存储删除入口。
- 在查询层完成权限限制，模板只负责呈现允许操作的记录。
- 不增加数据库迁移或依赖。

**Non-Goals:**

- 不增加批量删除、回收站或恢复机制。
- 不改变管理员删除流程、文献发布状态或元数据审核权限。
- 不重构现有页面样式体系。

## Decisions

1. **“我的上传”调用同一文献库视图流程。** 文献库视图接受内部的用户范围参数，“我的上传”入口传入当前用户；查询同时限制规范文献和预取附件。相比复制第二套模板和筛选逻辑，这能保证列表与筛选行为一致。
2. **筛选使用现有 GET 查询参数和 ORM。** 期刊、年份、上传者使用数据库中的 distinct 候选值，不引入表单类或新模型。无效年份不产生异常，只作为未命中条件处理。
3. **删除采用单条 POST。** 删除对象按 `pk + uploader=request.user` 获取，先调用现有存储删除函数，再删除上传记录；只有没有附件且没有外部引用时才清理规范文献。相比复用 admin action，这避免把管理员权限和后台请求语义带到用户页面。
4. **首页复用现有卡片样式。** 功能入口只链接到已存在页面，不新增聚合服务或配置层。

## Risks / Trade-offs

- [筛选候选随数据量增长] → 当前只读取去重的期刊、年份和实际上传用户；出现可测性能问题后再增加专门索引或异步搜索。
- [删除不可恢复] → 使用明确确认文案、仅 POST、所有权查询和“存储先行”顺序；本次不增加回收站。
- [同一规范文献含多人附件] → “我的上传”使用受限预取，确保其他用户附件不在该页面泄露或被误操作。

## Migration Plan

无需数据迁移。部署代码和模板后即可生效；回滚时恢复相关视图、URL、模板和测试文件。
